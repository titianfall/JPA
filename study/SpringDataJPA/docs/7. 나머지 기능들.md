## 0. 이 챕터의 한 줄 요약

> **"이런 기능도 있다" 소개 모음. 그리고 대부분의 결론은 똑같다 — 실무에서는 QueryDSL 을 쓴다.**

| 기능 | 한 줄 | 실무 판정 |
|---|---|---|
| Specifications (명세) | JPA Criteria 로 검색 조건을 조립 | ❌ Criteria 자체를 안 쓴다 → QueryDSL |
| Query By Example | 엔티티 인스턴스(Probe)를 조건으로 사용 | ❌ 매칭이 너무 단순 + LEFT JOIN 불가 |
| Projections | 엔티티 대신 필요한 필드만 조회 | ⚠️ **단순할 때만** 유용 |
| 네이티브 쿼리 | 진짜 어쩔 수 없을 때 SQL 직접 | ⚠️ 최후 수단, DTO 변환은 JdbcTemplate 권장 |

## 1. Specifications (명세) 🚧 미구현

### 개념

- DDD(도메인 주도 설계)의 **SPECIFICATION** 개념을 스프링 데이터 JPA가 **JPA Criteria** 로 지원한다.
- **술어(predicate)** = 참/거짓으로 평가되는 검색 조건 하나.
- 술어를 `and()` / `or()` / `not()` 으로 조합한다 → **컴포지트 패턴**.
- 타입: `org.springframework.data.jpa.domain.Specification`

### 사용 방법 — `JpaSpecificationExecutor` 상속

```java
public interface MemberRepository extends JpaRepository<Member, Long>,
        JpaSpecificationExecutor<Member> {
}
```

강의가 보여주는 `JpaSpecificationExecutor` (2.x):

```java
public interface JpaSpecificationExecutor<T> {
    Optional<T> findOne(@Nullable Specification<T> spec);
    List<T> findAll(Specification<T> spec);
    Page<T> findAll(Specification<T> spec, Pageable pageable);
    List<T> findAll(Specification<T> spec, Sort sort);
    long count(Specification<T> spec);
}
```

⚠️ **4.1.0 에서는 메서드가 더 늘었다** (실제 소스 확인):

```java
boolean exists(Specification<T> spec);
long update(UpdateSpecification<T> spec);          // 4.0 신규
long delete(DeleteSpecification<T> spec);          // 4.0 신규
Page<T> findAll(Specification<T> spec, Specification<T> countSpec, Pageable pageable);
<S extends T, R> R findBy(Specification<T> spec, Function<SpecificationFluentQuery<S>, R> queryFunction);
```

### 명세 정의 (강의 코드)

```java
public class MemberSpec {

    public static Specification<Member> teamName(final String teamName) {
        return (root, query, builder) -> {
            if (StringUtils.isEmpty(teamName)) {
                return null;
            }
            Join<Member, Team> t = root.join("team", JoinType.INNER); // 회원과 조인
            return builder.equal(t.get("name"), teamName);
        };
    }

    public static Specification<Member> username(final String username) {
        return (root, query, builder) -> builder.equal(root.get("username"), username);
    }
}
```

```java
Specification<Member> spec = MemberSpec.username("m1").and(MemberSpec.teamName("teamA"));
List<Member> result = memberRepository.findAll(spec);
```

- `Specification` 은 `toPredicate(root, query, builder)` **하나만** 구현하면 된다 → 람다로 축약.
- 파라미터는 JPA Criteria 의 `Root`, `CriteriaQuery`, `CriteriaBuilder`.

### ⚠️ 지금 환경에서 그대로 쓰면 안 되는 것

| 강의 코드 | 문제 | 지금 써야 할 것 |
|---|---|---|
| `StringUtils.isEmpty(teamName)` | 스프링 6에서 제거된 API | `!StringUtils.hasText(teamName)` |
| `Specification.where(null)` | **4.0부터 `Assert.notNull` 로 막힌다** | `Specification.unrestricted()` |
| `javax.persistence.criteria.*` | — | `jakarta.persistence.criteria.*` |
| `(Specification<Member>) (root, query, builder) -> ...` 캐스팅 | 불필요 | 캐스팅 없이 람다 그대로 |

`toPredicate` 시그니처 자체는 **그대로**다 (반환값도 여전히 `@Nullable`).

```java
@Nullable
Predicate toPredicate(Root<T> root, CriteriaQuery<?> query, CriteriaBuilder criteriaBuilder);
```

💡 4.0에서 추가된 편의 메서드들도 알아 두면 좋다.

```java
Specification.unrestricted()               // null 대신 "조건 없음"을 명시적으로 표현
Specification.allOf(spec1, spec2, spec3)   // 전부 AND
Specification.anyOf(spec1, spec2)          // 전부 OR
PredicateSpecification<T>                  // CriteriaQuery 가 필요 없을 때 쓰는 간소화 버전
```

> ⚠️ **참고: 실무에서는 JPA Criteria 를 거의 안 쓴다.** 코드만 봐서는 어떤 SQL 이 나가는지 알기 어렵다.
> **QueryDSL 을 쓰자.** (이 로드맵의 다음 강의)

## 2. Query By Example (QBE) 🚧 미구현

### 개념 — 엔티티 인스턴스 자체가 검색 조건

| 구성 요소 | 역할 |
|---|---|
| **Probe** | 필드에 값이 채워진 **실제 도메인 객체** (이게 곧 검색 조건) |
| **ExampleMatcher** | 어떤 필드를 무시할지/어떻게 매칭할지. 재사용 가능 |
| **Example** | Probe + ExampleMatcher → 쿼리 생성에 사용 |

`JpaRepository` 가 이미 `QueryByExampleExecutor` 를 상속하고 있어서 **추가 설정이 필요 없다.**

```java
@Test
public void basic() throws Exception {
    //given
    Team teamA = new Team("teamA");
    em.persist(teamA);
    em.persist(new Member("m1", 0, teamA));
    em.persist(new Member("m2", 0, teamA));
    em.flush();

    //when
    Member member = new Member("m1");      // Probe
    Team team = new Team("teamA");         // 내부 조인으로 teamA 조건 가능
    member.setTeam(team);

    ExampleMatcher matcher = ExampleMatcher.matching()
            .withIgnorePaths("age");       // age 는 primitive 라 0 이 조건으로 잡히므로 무시

    Example<Member> example = Example.of(member, matcher);
    List<Member> result = memberRepository.findAll(example);

    //then
    assertThat(result.size()).isEqualTo(1);
}
```

> 💡 `withIgnorePaths("age")` 가 필요한 이유:
> `age` 가 `int` 라 값을 안 넣어도 **0** 이 들어 있고, QBE 는 그걸 `age = 0` 조건으로 해석한다.
> **기본 타입 필드는 항상 무시 목록에 넣어야 한다.**

⚠️ 내 `Member` 는 연관관계 편의 메서드 `changeTeam()` 을 쓰지만, **Probe 를 만들 때는 `setTeam()` 이 맞다.**
`changeTeam()` 은 `team.getMembers().add(this)` 부수효과가 있어서, 검색 조건용 객체를 만들 뿐인데
영속 상태가 아닌 팀 컬렉션을 건드리게 된다.

### 장점 / 단점

| 장점 | 단점 |
|---|---|
| 동적 쿼리를 편하게 처리 | **내부 조인(INNER JOIN)만 된다. LEFT JOIN 불가** |
| 도메인 객체를 그대로 사용 | 중첩 제약조건 불가 — `a = ?0 or (a = ?1 and b = ?2)` |
| RDB → NoSQL 로 바꿔도 코드 동일 (추상화) | 매칭 조건이 단순: 문자열은 starts/contains/ends/regex, 나머지는 `=` 뿐 |
| `JpaRepository` 에 이미 포함 | |

> **정리: 실무에 쓰기엔 매칭 조건이 너무 단순하고 LEFT 조인이 안 된다 → QueryDSL.**

## 3. Projections 🚧 미구현

> **엔티티 전체가 아니라 필요한 필드만 조회하고 싶을 때.**

### ① 인터페이스 기반 — Closed Projection

```java
public interface UsernameOnly {
    String getUsername();   // getter 형식으로 원하는 필드만 선언
}
```

```java
public interface MemberRepository ... {
    List<UsernameOnly> findProjectionsByUsername(String username);
}
```

- **메서드 이름은 자유, 반환 타입으로 인지한다.**
- 구현체는 스프링 데이터 JPA 가 프록시로 만들어 준다.
- SQL 도 `select` 절이 최적화된다.

```sql
select m.username from member m where m.username = 'm1';
```

### ② 인터페이스 기반 — Open Projection (SpEL)

```java
public interface UsernameOnly {
    @Value("#{target.username + ' ' + target.age + ' ' + target.team.name}")
    String getUsername();
}
```

⚠️ **SpEL 을 쓰는 순간 select 절 최적화가 사라진다.**
DB 에서 **엔티티 필드를 전부 조회한 다음** 애플리케이션에서 계산하기 때문이다.
(SpEL·`@Value` 자체가 처음이면 → [spring-study/issues](https://github.com/titianfall/spring-study/tree/main/issues))

### ③ 클래스 기반 Projection (DTO)

```java
public class UsernameOnlyDto {

    private final String username;

    public UsernameOnlyDto(String username) {
        this.username = username;
    }

    public String getUsername() {
        return username;
    }
}
```

**생성자 파라미터 이름으로 매칭**한다.

> 💡 파라미터 이름이 `.class` 에 남아 있어야 매칭이 되는데(`-parameters` 컴파일 옵션),
> **스프링 부트 그래들 플러그인이 기본으로 켜 준다.** 내 `build/classes` 를 `javap -v` 로 열어 보니
> `MethodParameters` 속성에 `username` 같은 이름이 그대로 들어 있었다. 그래서 추가 설정 없이 동작한다.

### ④ 동적 Projections — 반환 타입을 파라미터로

```java
<T> List<T> findProjectionsByUsername(String username, Class<T> type);
```

```java
List<UsernameOnly> result = memberRepository.findProjectionsByUsername("m1", UsernameOnly.class);
```

### ⑤ 중첩 구조 — 여기서부터 최적화가 깨진다

```java
public interface NestedClosedProjection {
    String getUsername();
    TeamInfo getTeam();

    interface TeamInfo {
        String getName();
    }
}
```

```sql
select m.username, t.team_id, t.team_id, t.name
from member m
left outer join team t on m.team_id = t.team_id
where m.username = ?
```

| 프로젝션 대상 | 결과 |
|---|---|
| **root 엔티티** (`Member` 의 필드) | ✅ JPQL `select` 절 최적화됨 |
| **root 를 벗어남** (`Member.team` …) | ⚠️ **LEFT OUTER JOIN** + 해당 엔티티의 **모든 필드 select** 후 계산 |

> **정리**
> - root 엔티티면 유용하다.
> - root 를 넘어가면 select 최적화가 안 된다.
> - 실무의 복잡한 쿼리에는 한계가 있다 → **단순할 때만 쓰고, 조금만 복잡해지면 QueryDSL.**

## 4. 네이티브 쿼리 🚧 미구현

> **가급적 쓰지 않는 게 좋다. 정말 어쩔 수 없을 때만.**
> 최근의 궁극기는 **네이티브 쿼리 + 스프링 데이터 Projections 조합**.

### 스프링 데이터 JPA 기반 네이티브 쿼리

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    @Query(value = "select * from member where username = ?", nativeQuery = true)
    Member findByNativeQuery(String username);
}
```

| 지원 | 제약 |
|---|---|
| 페이징 지원 | `Sort` 파라미터 정렬이 정상 동작하지 않을 수 있다(믿지 말고 직접 처리) |
| 반환 타입: `Object[]`, `Tuple`, DTO(인터페이스 Projections) | JPQL 과 달리 **로딩 시점에 문법 검증 불가** (틀리면 런타임에 터진다) |
| | **동적 쿼리 불가** |

### ✅ 위치 파라미터 인덱스 — 강의와 결과가 다르다 (직접 확인)

강의는 *"JPQL 은 1부터, 네이티브 SQL 은 0부터"* 라고 설명한다.
**Hibernate 7.4.1 에서는 아니다.** 세 가지를 직접 돌려 봤다.

```java
em.createNativeQuery("select * from member where username = ?1", Member.class).setParameter(1, "nq1");
em.createNativeQuery("select * from member where username = ?",  Member.class).setParameter(1, "nq1");
em.createNativeQuery("select * from member where username = ?",  Member.class).setParameter(0, "nq1");
```

```
RESULT[?1 + setParameter(1)] = OK nq1
RESULT[? + setParameter(1)] = OK nq1
RESULT[? + setParameter(0)] = FAIL IllegalArgumentException
                                 : No parameter labelled '?0' in query with ordinal parameters [1]
```

→ **네이티브 쿼리도 위치 파라미터는 1부터**다. `0` 은 예외가 난다.
헷갈리지 않게 **`?1` 처럼 번호를 명시**하는 편이 낫다.

### 네이티브 SQL 을 DTO 로 받기가 어려운 이유

| 방법 | 평가 |
|---|---|
| JPA `Tuple` 로 조회 | 번거로움 |
| `Map` 으로 조회 | 타입 안전성 없음 |
| `@SqlResultSetMapping` | 복잡 |
| Hibernate `ResultTransformer` | 복잡 + ⚠️ **Hibernate 7 에서 deprecated** |
| **JdbcTemplate / MyBatis** | 👍 강의 권장 |

### 궁극의 방법 — 네이티브 쿼리 + 인터페이스 Projections

```java
@Query(value = "SELECT m.member_id as id, m.username, t.name as teamName " +
               "FROM member m left join team t ON m.team_id = t.team_id",
       countQuery = "SELECT count(*) from member",
       nativeQuery = true)
Page<MemberProjection> findByNativeProjection(Pageable pageable);
```

- `select` 의 **별칭(alias)** 을 프로젝션 인터페이스의 getter 이름과 맞추면 된다 (`t.name as teamName` ↔ `getTeamName()`).
- `countQuery` 를 따로 줘야 페이징이 제대로 동작한다.

### 동적 네이티브 쿼리

- 하이버네이트를 직접 활용하거나,
- 스프링 `JdbcTemplate`, MyBatis, jOOQ 같은 외부 라이브러리를 쓴다.

강의의 하이버네이트 코드:

```java
String sql = "select m.username as username from member m";

List<MemberDto> result = em.createNativeQuery(sql)
        .setFirstResult(0)
        .setMaxResults(10)
        .unwrap(NativeQuery.class)
        .addScalar("username")
        .setResultTransformer(Transformers.aliasToBean(MemberDto.class))   // ⚠️
        .getResultList();
```

⚠️ **`ResultTransformer` / `Transformers.aliasToBean()` 은 Hibernate 7 에서 `@Deprecated` 다.**
(클래스 자체는 아직 남아 있어서 컴파일은 되지만 경고가 뜬다. 실제 7.4.1 클래스에서 `Deprecated: true` 확인.)
Hibernate 6 부터 `ResultTransformer` 가 **`TupleTransformer`(행 변환) + `ResultListTransformer`(목록 변환)** 로 쪼개졌다.

```java
// Hibernate 6/7 방식
List<MemberDto> result = em.createNativeQuery(sql)
        .setFirstResult(0)
        .setMaxResults(10)
        .unwrap(NativeQuery.class)
        .addScalar("username", String.class)
        .setTupleTransformer((tuple, aliases) -> new MemberDto(null, (String) tuple[0], null))
        .getResultList();
```

## ✅ 핵심 요약

| 주제 | 결론 |
|---|---|
| Specifications | JPA Criteria 기반 조건 조립. `JpaSpecificationExecutor` 상속 → **실무에선 안 쓴다** |
| Query By Example | Probe + ExampleMatcher. INNER JOIN 만, 매칭 단순 → **실무에선 안 쓴다** |
| Projections | 인터페이스/클래스/동적/중첩 4가지. **root 엔티티까지만 최적화된다** |
| 네이티브 쿼리 | 최후 수단. **동적 쿼리 불가, 로딩 시점 문법 검증 불가** |
| 네이티브 + Projections | 별칭을 getter 이름에 맞추면 DTO 로 받을 수 있다. 페이징하려면 `countQuery` 필수 |
| 공통 결론 | **조금이라도 복잡하면 QueryDSL** (다음 강의) |

### ⚠️ 강의와 달라지는 지점 (직접 확인한 것)

| 항목 | 강의 (부트 2.x / Hibernate 5) | 내 환경 (부트 4.1.0 / Hibernate 7.4.1) |
|---|---|---|
| 패키지 | `javax.persistence.*` | **`jakarta.persistence.*`** |
| `Specification.where(null)` | 허용 | **금지(`Assert.notNull`) → `Specification.unrestricted()`** |
| `StringUtils.isEmpty()` | 사용 가능 | **제거됨 → `!StringUtils.hasText()`** |
| `JpaSpecificationExecutor` | 5개 메서드 | **`exists` / `update` / `delete` / `findBy`(fluent) 추가** |
| 네이티브 위치 파라미터 | "0부터" | **1부터 (0은 `IllegalArgumentException`)** |
| `setResultTransformer(Transformers.aliasToBean(...))` | 정상 | **`@Deprecated` → `setTupleTransformer(...)`** |
| 클래스 기반 Projection 의 `-parameters` | 별도 설정 필요할 수 있음 | **부트 그래들 플러그인이 기본 적용** |

### 구현할 때 만들 것 (체크리스트)

| 구분 | 파일 | 상태 |
|---|---|---|
| 명세 | `repository/MemberSpec.java` + `MemberRepository extends JpaSpecificationExecutor<Member>` | 🚧 |
| QBE | `QueryByExampleTest` | 🚧 |
| Projections | `repository/UsernameOnly`, `UsernameOnlyDto`, `NestedClosedProjection` | 🚧 |
| 네이티브 쿼리 | `MemberRepository.findByNativeQuery`, `findByNativeProjection` + `MemberProjection` | 🚧 |
