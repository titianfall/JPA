# 5. API 개발 고급 - 실무 필수 최적화 — OSIV와 커맨드/쿼리 분리

> `5. API 개발 고급 - 실무 필수 최적화.pdf` 강의자료를 기준으로 정리하고,
> 4장까지 내가 작성한 `OrderApiController`·`OrderRepository`·`OrderService` 코드에 대입해서 확인한다.
> Spring Boot 3.5.16, Java 17, Hibernate 6.6, `jakarta.persistence` 기준.
>
> 🚧 **이 장은 아직 코드로 옮기지 않았다.** `application.yml`에 `open-in-view` 설정이 없고 `OrderQueryService`도 만들지 않았다.
> 아래 "내 코드에 적용하면" 절은 **강의자료 기준의 예상**이며, 실제 실행으로 검증한 값이 아니다.
> (4장 문서의 쿼리 수는 전부 실측값이었지만, 이 장은 그렇지 않다는 점을 구분해 둔다.)

---

## 0. 이 챕터의 한 줄 요약

> **지금까지 컨트롤러에서 지연 로딩이 됐던 건 OSIV가 켜져 있어서다. 그리고 그 편의는 DB 커넥션을 응답 끝까지 붙잡는 대가로 얻은 것이다.**

3장·4장은 **쿼리 수**를 줄이는 이야기였다. 이 장은 **커넥션 점유 시간**을 줄이는 이야기다.
쿼리를 아무리 줄여도 커넥션이 모자라면 애플리케이션은 그대로 멈춘다.

---

## 1. OSIV란

| 이름 | 기술 |
|------|------|
| **O**pen **S**ession **I**n **V**iew | 하이버네이트 (`Session`) |
| **O**pen **E**ntity**M**anager **I**n **V**iew | JPA (`EntityManager`) |

이름은 둘이지만 개념은 같다. **관례상 OSIV라고 부른다.**

스프링 부트에서는 프로퍼티 하나로 제어한다.

```yaml
spring:
  jpa:
    open-in-view: true   # 기본값
```

---

## 2. OSIV ON — 기본값

### 부트가 굳이 경고를 찍는다

내 `application.yml`에는 `open-in-view` 설정이 **없다.** 즉 기본값 `true`로 켜져 있고,
그래서 애플리케이션을 띄울 때마다 `JpaBaseConfiguration$JpaWebConfiguration`이 이 `warn`을 남긴다.

```
spring.jpa.open-in-view is enabled by default. Therefore, database queries may be
performed during view rendering. Explicitly configure spring.jpa.open-in-view to
disable this warning
```

> 💡 "끄라"는 말이 아니라 **"켜져 있다는 걸 알고 쓰라, 그리고 명시적으로 설정해서 이 경고를 없애라"** 는 뜻이다.
> 켜든 끄든 `application.yml`에 **명시**하면 경고는 사라진다.

### 생명주기 — 커넥션을 언제까지 붙잡나

```
요청 ──▶ 컨트롤러 ──▶ 서비스(@Transactional) ──▶ 리포지토리 ──▶ DB
         │                │
         │                ├─ 트랜잭션 시작 ······· 커넥션 획득 ◀── 여기서 잡고
         │                └─ 트랜잭션 종료 ······· 커넥션 반환 ✗ (안 놓는다!)
         │
         ├─ 컨트롤러에서 지연 로딩 ····· ✅ 가능
         ├─ JSON 직렬화 / 뷰 렌더링 ···· ✅ 가능
         │
       응답 종료 ─────────────────────── 커넥션 반환 ◀── 여기서야 놓는다
```

핵심은 **"최초 데이터베이스 커넥션 시작 시점부터 API 응답이 끝날 때까지"** 영속성 컨텍스트와 데이터베이스 커넥션을 **함께** 유지한다는 것이다.

- 지연 로딩은 **영속성 컨텍스트가 살아 있어야** 동작한다.
- 영속성 컨텍스트는 기본적으로 **데이터베이스 커넥션을 유지**한다.
- 그래서 지금까지 `OrderApiController`의 V1/V2에서 컨트롤러 한복판에 지연 로딩 코드를 써도 아무 문제가 없었다.

### 그래서 뭐가 문제인가

⚠️ **너무 오랜 시간 동안 데이터베이스 커넥션 리소스를 점유한다.**

실시간 트래픽이 중요한 애플리케이션에서는 **커넥션이 모자라고, 결국 장애로 이어진다.**

가장 위험한 시나리오는 컨트롤러에서 **외부 API를 호출**하는 경우다.

```
[OSIV ON] 트랜잭션 끝 ──▶ 외부 결제 API 호출 (3초 대기) ──▶ 응답 렌더링 ──▶ 커넥션 반환
                          └────── 이 3초 내내 DB 커넥션을 붙잡고 있다 ──────┘
```

DB는 아무 일도 안 하는데 커넥션만 점유된다. 커넥션 풀(HikariCP 기본 10개)이 순식간에 마른다.

## 3. OSIV OFF

```yaml
spring:
  jpa:
    open-in-view: false
```

```
요청 ──▶ 컨트롤러 ──▶ 서비스(@Transactional) ──▶ 리포지토리 ──▶ DB
                      │
                      ├─ 트랜잭션 시작 ······· 커넥션 획득
                      └─ 트랜잭션 종료 ······· 커넥션 반환 ✅ + 영속성 컨텍스트 종료
         │
         ├─ 컨트롤러에서 지연 로딩 ····· ❌ LazyInitializationException
         └─ JSON 직렬화 / 뷰 렌더링 ···· ❌ 지연 로딩 불가
```

| | 얻는 것 | 잃는 것 |
|---|---|---|
| **OSIV OFF** | 커넥션 리소스를 낭비하지 않는다 | 모든 지연 로딩을 **트랜잭션 안에서** 처리해야 한다 |
| | 커넥션 점유 시간이 트랜잭션 길이로 줄어든다 | view template에서 지연 로딩이 **동작하지 않는다** |

⚠️ 결론적으로 **트랜잭션이 끝나기 전에 지연 로딩을 강제로 호출해 두어야 한다.**
지금까지 편하게 써 온 지연 로딩 코드를 전부 트랜잭션 안으로 옮겨야 한다는 뜻이고, 이게 OSIV OFF의 진짜 비용이다.

## 4. 내 코드에 대입하면 — 어디가 터지나 🚧

`OrderApiController`의 V1~V6 중 **OSIV를 끄는 순간 깨지는 것과 멀쩡한 것**이 갈린다.
기준은 단 하나 — **컨트롤러에서 지연 로딩이 일어나는가.**

| 버전 | 리포지토리 호출 | 컨트롤러에서 지연 로딩 | OSIV OFF 시 |
|------|----------------|:---:|:---:|
| V1 | `findAllByString()` | 강제 초기화로 직접 호출 | ❌ 깨짐 |
| V2 | `findAllByString()` | `OrderDto` 생성자에서 발생 | ❌ 깨짐 |
| V3 | `findAllWithItem()` | 없음 (`member`·`delivery`·`orderItems`·`oi.item` **전부 페치 조인**) | ✅ 안전 |
| V3.1 | `findAllWithMemberDelivery(offset, limit)` | `orderItems`가 배치로 **지연** 로딩 | ❌ 깨짐 |
| V4 | `findOrderQueryDtos()` | 없음 (DTO 직접 조회) | ✅ 안전 |
| V5 | `findAllByDto_optimization()` | 없음 (DTO 직접 조회) | ✅ 안전 |
| V6 | `findAllByDto_flat()` | 없음 (DTO 직접 조회) | ✅ 안전 |

> ⚠️ **V3.1이 함정이다.** 4장에서 "ToOne은 페치 조인, ToMany는 배치 사이즈"가 정답이라고 정리했는데,
> 그 배치 로딩이 결국 **지연 로딩**이다. `default_batch_fetch_size`는 쿼리 수를 줄여 줄 뿐 영속성 컨텍스트 밖에서 되살려 주지는 않는다.
> **4장의 권장안(V3.1)이 5장의 권장안(OSIV OFF)과 정면으로 부딪힌다** — 이 충돌을 푸는 게 다음 절이다.

🚧 위 표는 코드를 읽고 판단한 것이고, 실제로 `open-in-view: false`로 띄워서 확인하지는 않았다.

## 5. 커맨드와 쿼리 분리 (CQS)

> 참고: [Command–query separation](https://en.wikipedia.org/wiki/Command%E2%80%93query_separation)

실무에서 **OSIV를 끈 상태로 복잡성을 관리하는** 방법이다.

### 왜 나누나

| | 성격 | 성능 최적화 압박 | 비즈니스 중요도 |
|---|---|:---:|:---:|
| **Command** | 엔티티 몇 개를 등록/수정 | 낮음 | **높음** |
| **Query** | 복잡한 화면을 출력하기 위한 조회 | **높음** | 낮음 |

> 보통 비즈니스 로직은 특정 엔티티 몇 개를 등록하거나 수정하는 것이므로 성능이 크게 문제가 되지 않는다.
> 복잡한 화면을 출력하기 위한 쿼리는 화면에 맞추어 성능을 최적화 하는 것이 중요하지만,
> **그 복잡성에 비해 핵심 비즈니스에 큰 영향을 주는 것은 아니다.**

라이프사이클이 다르다. 화면은 자주 바뀌고 핵심 비즈니스 로직은 잘 안 바뀐다.
그래서 **크고 복잡한 애플리케이션**이라면 이 둘의 관심사를 분리하는 게 유지보수 관점에서 의미가 있다.

### 어떻게 나누나

```
OrderService        ← 핵심 비즈니스 로직 (Command)
OrderQueryService   ← 화면이나 API에 맞춘 서비스 (Query, 주로 읽기 전용 트랜잭션)
```

**보통 서비스 계층에서 트랜잭션을 유지한다. 두 서비스 모두 트랜잭션을 유지하면서 지연 로딩을 사용할 수 있다.**
이게 핵심이다 — OSIV를 꺼도 **서비스 안이면 트랜잭션이 살아 있으므로 지연 로딩이 된다.**

### 내 코드라면 이렇게 🚧

지금 `OrderApiController.ordersV3_page()`는 컨트롤러에서 DTO 변환(=지연 로딩)을 하고 있다.
이걸 서비스로 내리면 OSIV를 꺼도 V3.1이 그대로 동작한다.

```java
@Service
@Transactional(readOnly = true)   // 조회 전용
@RequiredArgsConstructor
public class OrderQueryService {

    private final OrderRepository orderRepository;

    // 트랜잭션 안이므로 OSIV가 꺼져 있어도 orderItems 지연 로딩이 살아 있다
    public List<OrderDto> ordersV3Page(int offset, int limit) {
        return orderRepository.findAllWithMemberDelivery(offset, limit).stream()
                .map(OrderDto::new)
                .collect(toList());
    }
}
```

```java
@GetMapping("/api/v3.1/orders")
public List<OrderDto> ordersV3_page(...) {
    return orderQueryService.ordersV3Page(offset, limit);   // 컨트롤러는 위임만
}
```

⚠️ 이때 `OrderDto`/`OrderItemDto`는 지금 `OrderApiController`의 **`static` 중첩 클래스**다.
서비스로 옮기면 별도 클래스로 빼내야 한다. 기존 `OrderService`(`@Transactional(readOnly = true)` + 쓰기 메서드만 `@Transactional`)와 이름이 겹치지 않게 **`OrderQueryService`로 분리**하는 게 이 절의 요지다.

Spring 기초(`@Transactional` 전파, 프록시, `readOnly`)는 [spring-study/issues](https://github.com/titianfall/spring-study/tree/main/issues) 참고.

## 6. 실무 선택 기준

> **필자는 고객 서비스의 실시간 API는 OSIV를 끄고, ADMIN 처럼 커넥션을 많이 사용하지 않는 곳에서는 OSIV를 켠다.**

| 상황 | OSIV | 이유 |
|------|:---:|------|
| 고객용 실시간 API | **OFF** | 트래픽이 많다. 커넥션이 곧 처리량 |
| ADMIN 백오피스 | **ON** | 동시 사용자가 적다. 개발 편의가 더 이득 |

즉 **정답이 하나가 아니라, 커넥션 경합이 있는 곳만 끄는** 실용적 판단이다.

> 💡 OSIV를 더 깊이 알고 싶으면 **자바 ORM 표준 JPA 프로그래밍 13장 「웹 애플리케이션과 영속성 관리」** 를 참고하자.
> (기본편 로드맵의 그 책이다.)

## ✅ 핵심 요약

| # | 핵심 | 근거 |
|---|------|------|
| 1 | OSIV = Open Session In View(하이버네이트) = Open EntityManager In View(JPA) | 관례상 OSIV |
| 2 | `spring.jpa.open-in-view`의 **기본값은 `true`** | 부트가 시작 시 `warn` 로그를 남긴다 |
| 3 | 경고를 없애려면 **켜든 끄든 명시적으로 설정**하면 된다 | "Explicitly configure ... to disable this warning" |
| 4 | OSIV ON은 **최초 커넥션 시점 ~ API 응답 종료**까지 커넥션을 유지 | 그래서 컨트롤러 지연 로딩이 됐던 것 |
| 5 | 지연 로딩은 **영속성 컨텍스트**가, 영속성 컨텍스트는 **커넥션**이 있어야 산다 | ON의 장점이자 단점의 원인 |
| 6 | OSIV의 대가는 **커넥션 점유 시간** — 실시간 트래픽에선 장애로 이어진다 | 컨트롤러에서 외부 API 호출 시 최악 |
| 7 | OSIV OFF는 **트랜잭션 종료 시 커넥션 반환 + 영속성 컨텍스트 종료** | 커넥션 낭비 없음 |
| 8 | OSIV OFF면 **모든 지연 로딩을 트랜잭션 안에서** 끝내야 한다 | view template 지연 로딩 불가 |
| 9 | 내 코드 기준 **V1·V2·V3.1이 깨지고, V3·V4·V5·V6은 안전**하다 🚧 | 컨트롤러 지연 로딩 유무 |
| 10 | **4장의 정답(V3.1 배치)과 5장의 정답(OSIV OFF)이 충돌**한다 | 배치 로딩도 결국 지연 로딩 |
| 11 | 해법은 **커맨드와 쿼리 분리** — `OrderService` / `OrderQueryService` | 서비스 안이면 트랜잭션이 살아 있다 |
| 12 | Query 서비스는 **읽기 전용 트랜잭션**을 쓴다 | `@Transactional(readOnly = true)` |
| 13 | 실무에선 **실시간 API는 OFF, ADMIN은 ON** | 커넥션 경합이 있는 곳만 끈다 |

> 다음 6장은 「다음으로」 — 로드맵 마무리와 스프링 데이터 JPA / Querydsl로 넘어가는 안내다.
