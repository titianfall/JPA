# 3. API 개발 고급 - 지연 로딩과 조회 성능 최적화 — 간단한 주문 조회 V1~V4

> `3. API 개발 고급 - 지연 로딩과 조회 성능 최적화.pdf` 강의자료와, 내가 작성한 `OrderSimpleApiController`·`OrderRepository`·`OrderSimpleQueryRepository` 코드를 기준으로 정리한다.
> Spring Boot 3.5.16, Java 17, Hibernate 6.6, `jakarta.persistence` 기준.
>
> ✅ 이 문서의 **쿼리 수는 전부 실제로 호출해서 센 값**이다. 2장에서 만든 주문 2건(userA, userB) 기준.

---

## 0. 이 챕터의 한 줄 요약

> **주문 + 배송정보 + 회원을 조회하는 API를 만들면, 지연 로딩 때문에 성능 문제가 발생한다. 이걸 단계적으로 해결한다.**

이 장에서 다루는 연관관계는 **`xToOne`** 뿐이다.

```
Order ──@ManyToOne(LAZY)──▶ Member
      └─@OneToOne (LAZY)──▶ Delivery
```

`Order → OrderItem`(`@OneToMany`, 컬렉션)은 **4장**에서 따로 다룬다. 컬렉션은 조인하는 순간 결과 행이 뻥튀기되기 때문에 문제의 성격 자체가 다르다. 그래서 이 장은 `OrderSimple`이라는 이름을 쓴다.

### 결론 먼저 — 실측 결과

| 버전 | 엔드포인트 | 방식 | **쿼리 수** |
|------|-----------|------|-----------|
| V1 | `/api/v1/simple-orders` | 엔티티 직접 노출 | **7** |
| V2 | `/api/v2/simple-orders` | 엔티티를 DTO로 변환 | **5** |
| V3 | `/api/v3/simple-orders` | DTO 변환 + 페치 조인 | **1** |
| V4 | `/api/v4/simple-orders` | JPA에서 DTO로 바로 조회 | **1** |

V2→V3에서 5개가 1개로 떨어지는 게 이 장의 핵심이다. **V1→V2는 쿼리가 거의 안 줄어든다**는 것도 똑같이 중요하다.

> ⚠️ 강의에서 못 박는 말: **"지금부터 설명하는 내용은 정말 중요합니다. 실무에서 JPA를 사용하려면 100% 이해해야 합니다."**

## 1. V1 — 엔티티를 직접 노출

```java
// 내 코드 (OrderSimpleApiController)
/**
 * V1. 엔티티 직접 노출
 * - Hibernate5Module 모듈 등록, LAZY=null 처리
 * - 양방향 관계 문제 발생 -> @JsonIgnore
 */
@GetMapping("/api/v1/simple-orders")
public List<Order> ordersV1() {
    List<Order> all = orderRepository.findAllByString(new OrderSearch());
    for (Order order : all) {
        order.getMember().getName(); //Lazy 강제 초기화
        order.getDelivery().getAddress(); //Lazy 강제 초기화
    }
    return all; // member, delivery가 건드려져야함
}
```

`findAllByString(new OrderSearch())`는 [활용 1편 6장](../활용1/06.%20주문%20도메인%20개발.md)에서 만든 동적 쿼리 메서드다. `OrderSearch`를 빈 객체로 넘기면 조건이 하나도 안 붙어서 전체 조회가 된다.

```java
// 내 코드 (OrderRepository)
public List<Order> findAllByString(OrderSearch orderSearch) {
    String jpql = "select o from Order o join o.member m";
    ...
}
```

⚠️ 여기서 `join o.member m`은 **JPQL 조인일 뿐, `Member`를 함께 조회(select)하지 않는다.** 실제로 나가는 SQL을 보면 `select`에 `o1_0.*`만 있다.

```sql
select o1_0.order_id, o1_0.delivery_id, o1_0.member_id, o1_0.order_date, o1_0.order_status
from orders o1_0
  join member m1_0 on m1_0.member_id = o1_0.member_id   -- 조인은 했지만 select 안 함
fetch first 1000 rows only
```

**조인을 걸어도 `member`는 여전히 프록시로 남는다.** 이 착각이 N+1을 못 보게 만드는 첫 번째 함정이다. 함께 조회하려면 `join fetch`여야 한다(V3).

## 3. 🔥 문제 1 — 프록시를 JSON으로 만들 수 없다

### 실제로 만난 에러

강제 초기화 루프 없이 `return all;`만 쓰고 호출했더니 바로 500이 떨어졌다.

```
com.fasterxml.jackson.databind.exc.InvalidDefinitionException:
No serializer found for class org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor
and no properties discovered to create BeanSerializer
(through reference chain:
   java.util.ArrayList[0]->jpabook.jpashop.domain.Order["member"]
   ->jpabook.jpashop.domain.Member$HibernateProxy["hibernateLazyInitializer"])
```

마지막 참조 체인이 원인을 그대로 알려준다 — `Order`의 `member`가 **`Member`가 아니라 `Member$HibernateProxy`** 다.

### 왜 프록시인가

`Order`의 `xToOne` 연관관계는 활용 1편에서 전부 `LAZY`로 바꿔 놨다.

```java
// 내 코드 (Order)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "member_id")
private Member member;

@OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL)
@JoinColumn(name = "delivery_id")
private Delivery delivery;
```

지연 로딩이면 **DB에서 실제 `Member`를 조회하지 않는다.** 대신 하이버네이트가 만든 프록시 객체를 심어 둔다.

```mermaid
flowchart LR
    O["Order (진짜 엔티티)"] -->|member| P["Member$HibernateProxy<br/>ByteBuddyInterceptor"]
    P -.->|getName() 호출 시| DB[("DB 조회")]
    style P fill:#ffe0e0,color:#1a1a1a,stroke:#5a6270,stroke-width:1px
```

Jackson은 이 타입을 모르니 직렬화에 실패한다.

### 해결 방법 두 가지

| 방법 | 설명 |
|------|------|
| **A. 강제 초기화** | `order.getMember().getName()` 호출로 프록시를 실제 엔티티로 채운다 |
| **B. Hibernate 모듈 등록** | 초기화 안 된 프록시는 `null`로 출력하도록 Jackson에 알려준다 (4절) |

V1 컨트롤러의 두 줄이 A다.

```java
order.getMember().getName();      // Lazy 강제 초기화
order.getDelivery().getAddress(); // Lazy 강제 초기화
```

💡 `getMember()`만 호출하면 **초기화되지 않는다.** 프록시는 껍데기를 반환할 뿐이고, `getName()`처럼 **실제 값이 필요한 메서드**를 호출해야 그 순간 DB 조회가 나간다. 프록시 동작 원리는 [기본편 8장 프록시와 연관관계 관리](../../jpaBasic/08.%20프록시와%20연관관계%20관리.md)에 정리해 뒀다.

## 4. 해결책 B — Hibernate 모듈 등록 (⚠️ 버전 주의)

```java
// 내 코드 (JpashopApplication)
@Bean
Hibernate6Module hibernate6Module() {
    Hibernate6Module module = new Hibernate6Module();
//	module.configure(Hibernate6Module.Feature.FORCE_LAZY_LOADING, true);
    return module;
}
```

```gradle
// 내 코드 (build.gradle)
// 초기화 안 된 지연 로딩 프록시를 null 로 직렬화
// 강의는 hibernate5(부트 2.x) 지만 이 프로젝트는 부트 3.5 + Hibernate 6 이라 hibernate6 를 쓴다.
// 버전은 스프링 부트 BOM 이 Jackson 버전에 맞춰 관리한다.
implementation 'com.fasterxml.jackson.datatype:jackson-datatype-hibernate6'
```

### 여기가 강의와 가장 크게 갈리는 지점 — 버전 매트릭스

모듈 이름이 **부트/하이버네이트 버전마다 다르다.** 강의는 부트 2.x 기준이라 그대로 따라 하면 안 된다.

| 환경 | 의존성 | `@Bean` 클래스 |
|------|--------|---------------|
| 부트 2.x (`javax`) | `jackson-datatype-hibernate5` | `Hibernate5Module` |
| 부트 3.x + Hibernate **5** (`jakarta`) | `jackson-datatype-hibernate5-jakarta` | `Hibernate5JakartaModule` |
| **부트 3.5 + Hibernate 6** ← 내 환경 | `jackson-datatype-hibernate6` | **`Hibernate6Module`** |

부트 3.0부터 `javax` → `jakarta`로 바뀌었기 때문에, 부트 3.x에서 구버전 `hibernate5`를 쓰면 이렇게 터진다.

```
java.lang.ClassNotFoundException: javax.persistence.Transient
```

💡 버전을 명시하지 않아도 **스프링 부트 BOM이 Jackson과 같은 버전으로 맞춰준다.** 실제 해석 결과는 `jackson-datatype-hibernate6:2.21.4`(= `jackson-core`와 동일), `hibernate-core:6.6.53.Final`이었다.

### ⚠️ 모듈은 에러만 막을 뿐, 데이터를 가져다주지 않는다

모듈만 등록하고 강제 초기화를 빼면 500은 사라지지만 응답이 이렇게 나온다.

```json
[
  { "id": 1, "member": null, "delivery": null, "orderItems": null,
    "orderDate": "...", "orderStatus": "ORDER", "totalPrice": 50000 }
]
```

모듈의 규칙은 하나다 — **초기화된 프록시만 값으로 출력하고, 초기화 안 된 프록시는 `null`로 출력한다.** 아무도 `member`를 건드리지 않았으니 `null`이다. 값을 채우려면 결국 누군가 프록시를 깨워야 한다.

### 강제 지연 로딩 옵션 — 있지만 쓰지 마라

```java
module.configure(Hibernate6Module.Feature.FORCE_LAZY_LOADING, true);
```

`FORCE_LAZY_LOADING = true`는 **모든 지연 로딩을 전부 끌어온다.** 편해 보이지만 최악이다.

- `order → member`, `member → orders` 양방향 연관관계를 **계속 로딩**한다.
- 필요 없는 데이터까지 전부 조회하니 쿼리가 걷잡을 수 없이 늘어난다.

그래서 내 코드에도 주석으로만 남겨 뒀다.

## 5. 🔥 문제 2 — 양방향 연관관계의 JSON 무한 루프

엔티티를 직접 반환하면 Jackson이 객체 그래프를 **끝까지 따라간다.** 양방향이면 끝이 없다.

```
Order → member   → orders → member   → ... 💥
Order → delivery → order  → delivery → ... 💥
Order → orderItems → order → orderItems → ... 💥
```

1장에서 `Member`에만 걸어 놨던 걸, 이번에 나머지 두 곳에도 추가했다.

```java
// 내 코드 (Delivery)
@JsonIgnore // 양방향 연관관계 — Order 로 되돌아가는 무한 루프 차단
@OneToOne(mappedBy = "delivery", fetch = FetchType.LAZY)
private Order order;
```

```java
// 내 코드 (OrderItem)
@JsonIgnore // 양방향 연관관계 — Order 로 되돌아가는 무한 루프 차단
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id")
private Order order;
```

| 엔티티 | 필드 | `@JsonIgnore` |
|--------|------|--------------|
| `Member` | `orders` | ✅ (1장에서) |
| `Delivery` | `order` | ✅ (이번에 추가) |
| `OrderItem` | `order` | ✅ (이번에 추가) |

⚠️ **엔티티를 직접 노출할 때 양방향 연관관계는 반드시 한 곳을 `@JsonIgnore` 처리해야 한다.**

⚠️ 그런데 이건 **본질적으로 잘못된 처방**이다. `@JsonIgnore`는 순수한 도메인 엔티티에 **API 표현 관심사를 침투시키는 어노테이션**이다. → 그래서 V2에서 DTO로 간다.

## 6. ⚠️ 절대 하면 안 되는 해결책 — EAGER로 바꾸기

"지연 로딩이 문제니까 즉시 로딩으로 바꾸면 되지 않나?" — **안 된다.**

| 이유 | 설명 |
|------|------|
| 필요 없는 조회 | 연관관계가 필요 없는 API에서도 데이터를 **항상** 조회한다 |
| 성능 튜닝 불가 | 어디서 어떤 쿼리가 나갈지 **예측이 안 된다** |
| JPQL의 함정 | `select o from Order o` 한 줄이 **N+1 쿼리로 폭발**한다 |

특히 마지막이 치명적이다. `EAGER`여도 **JPQL은 즉시 로딩을 고려하지 않고** 일단 `select * from orders`를 그대로 날린다. 그 후에야 결과 N건 각각에 대해 추가 쿼리를 날린다.

> ✅ **원칙: 항상 지연 로딩을 기본으로 하고, 성능 최적화가 필요한 경우에는 페치 조인(fetch join)을 사용해라!**

## 7. 📊 V1 실측 — 쿼리 7번 (예상보다 2개 더)

`/api/v1/simple-orders` 호출 시 실제로 나간 쿼리다.

| 대상 | 횟수 | 이유 |
|------|-----|------|
| `orders` | 1 | `findAllByString` |
| `member` | 2 | 강제 초기화 (주문당 1) |
| `delivery` | 2 | 강제 초기화 (주문당 1) |
| **`order_item`** | **2** | **`getTotalPrice()`** |
| **합계** | **7** | |

`1 + N + N`이면 5여야 하는데 **7이 나왔다.** 나머지 2개는 `order_item` 조회다.

### 🔥 범인은 `getTotalPrice()`

```java
// 내 코드 (Order)
public int getTotalPrice() {
    int totalPrice = 0;
    for(OrderItem orderItem : orderItems) {   // ← 컬렉션 순회 = 지연 로딩 초기화
        totalPrice += orderItem.getTotalPrice();
    }
    return totalPrice;
}
```

`Order`에 `totalPrice`라는 **필드는 없다.** 그런데 응답에는 있다.

```json
{ "id": 1, ..., "orderItems": null, "totalPrice": 50000 }
```

**Jackson은 필드가 아니라 getter를 기준으로 JSON 속성을 만든다.** `getTotalPrice()`가 있으니 `totalPrice`라는 속성이 생기고, 그 getter가 `orderItems`를 순회하면서 지연 로딩을 초기화한다. 주문 2건이니 `order_item` 쿼리 2번.

⚠️ 응답이 앞뒤가 안 맞는 것도 이 때문이다. Jackson이 `orderItems`를 **먼저** 직렬화할 때는 미초기화 상태라 `null`로 나가고, 그 **뒤에** `totalPrice`를 계산하면서 컬렉션을 채운다. 같은 응답 안에서 "주문 상품은 없는데 총액은 50000원"인 모순이 생긴다.

> 💡 이게 엔티티 직접 노출의 가장 무서운 점이다. **의도하지 않은 계산 메서드가 API 스펙에 딸려 나오고, 그게 조용히 추가 쿼리를 만든다.** 컨트롤러 코드만 봐서는 절대 안 보인다.

## 8. V2 — 엔티티를 DTO로 변환

```java
// 내 코드 (OrderSimpleApiController)
@GetMapping("/api/v2/simple-orders")
public List<SimpleOrderDto> orderV2() {
    List<Order> orders = orderRepository.findAllByString(new OrderSearch());
    List<SimpleOrderDto> result = orders.stream()
            .map(order -> new SimpleOrderDto(order))
            .collect(Collectors.toList());

    return result;
}

@Data
static class SimpleOrderDto {
    private Long orderId;
    private String name;
    private LocalDateTime orderDate;
    private OrderStatus orderStatus;
    private Address address;

    public SimpleOrderDto(Order order) {
        orderId = order.getId();
        name = order.getMember().getName();
        orderDate = order.getOrderDate();
        orderStatus = order.getOrderStatus();
        address = order.getDelivery().getAddress();
    }
}
```

응답이 깔끔해진다.

```json
[{"orderId":1,"name":"userA","orderDate":"...","orderStatus":"ORDER",
  "address":{"city":"서울","street":"1","zipcode":"1111"}}]
```

DTO로 바꾸는 순간 3~5절의 문제가 **전부 사라진다.**

| 문제 | V2에서는? |
|------|----------|
| 프록시 직렬화 예외 | DTO 생성자가 `getName()`을 호출하므로 애초에 프록시가 JSON에 안 감 |
| 무한 루프 | DTO에 역방향 참조가 없음 |
| `totalPrice` 딸려 나옴 | DTO에 없는 필드는 안 나감 → **`order_item` 쿼리 2번도 사라짐** |
| 비밀번호 등 노출 | 필요한 필드만 담음 |

⚠️ **강의와 다른 점** — 강의는 `order.getStatus()`지만 내 `Order`의 필드명은 `orderStatus`라 **`getOrderStatus()`** 를 써야 한다.

⚠️ **작성하면서 낸 버그** — 처음에 `address = order.getMember().getAddress()`로 썼다. 컴파일도 되고 응답도 그럴듯하게 나오지만 **회원의 현재 주소**가 실린다. 2장에서 정리했듯 배송지는 주문 시점 주소를 복사해 박제한 값이라, 회원이 이사하면 과거 주문의 배송지가 바뀐 것처럼 보인다. 게다가 `delivery`를 아무도 안 건드리니 **배송 쿼리가 안 나가서** 쿼리 수만 보면 오히려 최적화된 것처럼 착각하게 된다.

### 📊 V2 실측 — 쿼리 5번

| 대상 | 횟수 |
|------|-----|
| `orders` | 1 |
| `member` | 2 |
| `delivery` | 2 |
| **합계** | **5** |

**딱 `1 + N + N`이다.** V1의 7개에서 2개가 준 건 순전히 `getTotalPrice()`가 사라진 덕분이고, **N+1 문제 자체는 하나도 해결되지 않았다.**

> ✅ **V2의 교훈: DTO는 API 스펙 문제를 푸는 도구지 성능 도구가 아니다.** 이 둘은 별개다.

💡 지금은 userA·userB가 서로 다른 회원이라 회원 쿼리가 2번 나갔다. **같은 회원이 주문 2건**을 했다면 영속성 컨텍스트 1차 캐시가 잡아줘서 1번만 나간다. 그래서 N+1은 "항상 N번"이 아니라 **"최악의 경우 N번"** 이다.

### 왜 N+1이 문제인가

주문 2건에 로컬 H2면 `took 0ms`라 문제가 안 보인다. 하지만 쿼리 수가 주문 수에 **비례**한다는 게 핵심이다.

| 주문 수 | 쿼리 수 |
|---|---|
| 2건 | 5 |
| 100건 | 201 |
| 1,000건 | 2,001 |

실무에서는 DB가 다른 서버에 있어서 쿼리마다 네트워크 왕복이 붙는다. 1번에 1ms만 잡아도 주문 1000건이면 응답 하나에 2초다. **DB는 전혀 안 바쁜데 왕복 대기만으로.**

## 9. V3 — 페치 조인 최적화 ⭐

```java
// 내 코드 (OrderRepository)
// LAZY 로딩 무시 프록시 대신 실제 객체
public List<Order> findAllWithMemberDelivery() {
    return em.createQuery("select o from Order o" +
                            " join fetch o.member m" +
                            " join fetch o.delivery d", Order.class)
            .getResultList();
}
```

```java
// 내 코드 (OrderSimpleApiController)
@GetMapping("/api/v3/simple-orders")
public List<SimpleOrderDto> orderV3() {
    List<Order> orders = orderRepository.findAllWithMemberDelivery();
    List<SimpleOrderDto> result = orders.stream()
            .map(order -> new SimpleOrderDto(order))
            .collect(Collectors.toList());

    return result;
}
```

**컨트롤러는 V2와 한 글자만 다르다** — 리포지토리 메서드 이름뿐이다. `SimpleOrderDto`도 그대로 재사용한다. 그런데 쿼리가 **5개 → 1개**가 된다.

### 📊 V3 실측 — 쿼리 1번

```sql
select o1_0.order_id,
       d1_0.delivery_id, d1_0.city, d1_0.street, d1_0.zipcode, d1_0.delivery_status,
       m1_0.member_id, m1_0.city, m1_0.street, m1_0.zipcode, m1_0.name,
       o1_0.order_date, o1_0.order_status
from orders o1_0
  join member   m1_0 on m1_0.member_id   = o1_0.member_id
  join delivery d1_0 on d1_0.delivery_id = o1_0.delivery_id
```

1절의 SQL과 비교하면 차이가 명확하다.

| | `join` (V1·V2) | `join fetch` (V3) |
|---|---|---|
| SQL 조인 | O | O |
| **`select`에 포함** | **X** | **O** |
| 결과 | `member`는 프록시 | `member`는 **실제 엔티티** |
| 추가 쿼리 | N번 | **0번** |

`join fetch`는 **연관 엔티티를 SQL `select`에 함께 넣어서 한 번에 조회**한다. 이미 값이 채워졌으니 지연 로딩이 발동할 일이 없다. 페치 조인은 [기본편 10장 객체지향 쿼리 언어](../../jpaBasic/10.2%20객체지향%20쿼리%20언어.md)에 정리해 뒀다.

> ✅ **페치 조인은 실무 필수다.** 이 장에서 딱 하나만 가져간다면 이것.

## 10. V4 — JPA에서 DTO로 바로 조회

V3까지는 `Order` **엔티티**를 조회한 뒤 DTO로 바꿨다. V4는 **처음부터 DTO로 조회**한다.

```java
// 내 코드 (OrderSimpleQueryRepository)
public List<OrderSimpleQueryDto> findOrderDtos() {
    return em.createQuery("select new jpabook.jpashop.repository.order.simplequery.OrderSimpleQueryDto(o.id, m.name, o.orderDate, o.orderStatus, d.address)" +
                    " from Order o" +
                    " join o.member m" +
                    " join o.delivery d", OrderSimpleQueryDto.class)
            .getResultList();
}
```

```java
// 내 코드 (OrderSimpleQueryDto)
@Data
public class OrderSimpleQueryDto {
    private Long orderId;
    private String name;
    private LocalDateTime orderDate;
    private OrderStatus orderStatus;
    private Address address;

    public OrderSimpleQueryDto(Long orderId, String name, LocalDateTime orderDate,
                               OrderStatus orderStatus, Address address) { ... }
}
```

`select new 패키지.클래스(...)`는 JPQL의 **생성자 표현식**이다. 반드시 **패키지명을 전부 적어야 하고**, DTO에 **파라미터 순서가 정확히 일치하는 생성자**가 있어야 한다.

⚠️ V4는 `join fetch`가 아니라 그냥 `join`이다. 엔티티가 아니라 스칼라 값을 뽑아 생성자에 넣는 것이라 페치 조인이 필요 없다.

### 📊 V4 실측 — 쿼리 1번, 하지만 SELECT가 다르다

```sql
select o1_0.order_id, m1_0.name, o1_0.order_date, o1_0.order_status,
       d1_0.city, d1_0.street, d1_0.zipcode
from orders o1_0
  join member   m1_0 on ...
  join delivery d1_0 on ...
```

V3와 나란히 놓으면 차이가 보인다.

| | V3 (페치 조인) | V4 (DTO 직접 조회) |
|---|---|---|
| 쿼리 수 | 1 | 1 |
| SELECT 컬럼 | **13개** (엔티티 전체) | **7개** (필요한 것만) |
| 가져오는 것 | `Order`·`Member`·`Delivery` 전부 | 화면에 쓸 값만 |

V3는 `member_id`, `delivery_id`, `delivery_status`처럼 **응답에 안 쓰는 컬럼까지** 가져온다. V4는 딱 필요한 것만 가져온다.

### 🔑 V3 vs V4 — 트레이드오프

| | V3 페치 조인 | V4 DTO 직접 조회 |
|---|---|---|
| 반환 | **엔티티** | DTO |
| 재사용성 | ⭕ 다른 API에서도 씀 | ❌ 이 API 전용 |
| 변경 감지 | ⭕ 가능 (더티 체킹) | ❌ 불가 (엔티티 아님) |
| SELECT 최적화 | ❌ 전체 컬럼 | ⭕ 필요한 컬럼만 |
| 리포지토리 재사용 | ⭕ | ❌ API 스펙이 리포지토리에 침투 |

**V4가 항상 낫지 않다.** 컬럼 몇 개 줄이는 이득은 생각보다 작고(네트워크 용량 문제일 뿐, 쿼리 수는 같다), 대신 **리포지토리가 특정 화면에 종속**된다. `OrderSimpleQueryDto`가 바뀌면 리포지토리도 고쳐야 한다.

### 📁 패키지를 분리한 이유

```
repository/
├── OrderRepository.java              ← 엔티티 조회 (V1·V2·V3)
└── order/simplequery/
    ├── OrderSimpleQueryRepository.java   ← 화면 전용 DTO 조회 (V4)
    └── OrderSimpleQueryDto.java
```

`OrderRepository`는 **엔티티 조회용**인데 화면 전용 DTO 조회 메서드가 섞이면 용도가 뒤죽박죽이 된다. 그래서 강의도 패키지를 따로 판다.

💡 내 `OrderSimpleQueryRepository`에 붙인 `@Data`는 불필요하다. getter/setter/`equals`/`toString`을 만드는 어노테이션인데 리포지토리는 상태를 노출할 일이 없다. `@Repository @RequiredArgsConstructor`면 충분하다.

### 🔥 작성하면서 낸 컴파일 에러

```java
private final OrderSimpleQueryDto orderSimpleQueryDto;      // ❌ DTO는 스프링 빈이 아님
return orderRepository.order.simplequery.findOrderDtos();   // ❌ 패키지 경로를 필드 접근처럼 씀
```

`order.simplequery`는 **패키지 이름**이지 `OrderRepository`의 필드가 아니다. 주입받아야 할 건 `OrderSimpleQueryRepository`다.

```java
private final OrderSimpleQueryRepository orderSimpleQueryRepository;   // ✅
return orderSimpleQueryRepository.findOrderDtos();                     // ✅
```

`OrderSimpleQueryDto`는 `@Repository`가 아니라 그냥 데이터를 담는 클래스라 빈이 아니다. 그대로 뒀다면 컴파일은 통과해도 기동 시 `NoSuchBeanDefinitionException`이 났을 것이다.

## 11. ✅ 쿼리 방식 선택 권장 순서

강의가 제시하는 순서다. **위에서부터 시도하고, 안 되면 내려간다.**

1. **엔티티를 DTO로 변환**하는 방법을 선택한다. (V2)
2. 필요하면 **페치 조인으로 성능을 최적화**한다 — 대부분의 성능 이슈가 해결된다. (V3)
3. 그래도 안 되면 **DTO로 직접 조회**하는 방법을 사용한다. (V4)
4. 최후의 방법은 JPA가 제공하는 **네이티브 SQL이나 스프링 JDBC Template**을 사용해서 SQL을 직접 사용한다.

> ⚠️ **2번에서 대부분 끝난다.** V4까지 가는 건 그만큼 드물다는 뜻이다.

| 7 | `EAGER`로 바꾸면 **더 나빠진다** | JPQL이 즉시 로딩을 무시하고 N+1을 그대로 만듦 |
| 8 | **V2는 성능을 개선하지 못한다** | 7 → 5, N+1은 그대로 |
| 9 | **V3 페치 조인이 진짜 해법** | 5 → 1, 컨트롤러는 거의 그대로 |
