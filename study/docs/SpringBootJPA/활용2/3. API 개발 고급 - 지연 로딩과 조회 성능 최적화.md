# 3. API 개발 고급 - 지연 로딩과 조회 성능 최적화 — 간단한 주문 조회 V1

> `3. API 개발 고급 - 지연 로딩과 조회 성능 최적화.pdf` 강의자료와, 활용 1편에서 만든 `Order`·`Member`·`Delivery` 도메인 및 `OrderRepository`를 기준으로 정리한다.
> Spring Boot 3.5.16, Java 17, Hibernate 6.x, `jakarta.persistence` 기준.
>
> 🚧 **이 문서는 V1 절만 정리한 상태다.** `OrderSimpleApiController`는 아직 `src/main/java/jpabook/jpashop/api/`에 없다(현재 `MemberApiController`만 존재). 따라서 아래 컨트롤러 코드는 **강의자료 기준**이며, 내 코드로 옮긴 뒤 실제 실행 로그와 함께 보강한다. V2~V4는 `🚧 미구현`으로 자리만 잡아 뒀다.

---

## 0. 이 챕터의 한 줄 요약

> **주문 + 배송정보 + 회원을 조회하는 API를 만들면, 지연 로딩 때문에 성능 문제가 발생한다. 이걸 단계적으로 해결한다.**

[2장](./2.%20API%20개발%20고급%20-%20준비.md)에서 만든 **주문 2건**을 이제 조회한다. 이 장에서 다루는 연관관계는 **`xToOne`** 뿐이다.

```
Order ──@ManyToOne(LAZY)──▶ Member
      └─@OneToOne (LAZY)──▶ Delivery
```

`Order → OrderItem`(`@OneToMany`, 컬렉션)은 **4장**에서 따로 다룬다. 컬렉션은 조인하는 순간 결과 행이 뻥튀기되기 때문에 문제의 성격 자체가 다르다. 그래서 이 장은 `OrderSimple`이라는 이름을 쓴다.

이 장의 진행 순서는 이렇다.

| 버전 | 방식 | 상태 |
|------|------|------|
| **V1** | 엔티티를 직접 노출 | ✅ 이번 정리 |
| V2 | 엔티티를 DTO로 변환 | 🚧 미구현 |
| V3 | DTO 변환 + 페치 조인 최적화 | 🚧 미구현 |
| V4 | JPA에서 DTO로 바로 조회 | 🚧 미구현 |

> ⚠️ 강의에서 못 박는 말: **"지금부터 설명하는 내용은 정말 중요합니다. 실무에서 JPA를 사용하려면 100% 이해해야 합니다."**

## 1. V1 — 엔티티를 직접 노출

### 컨트롤러

```java
// 강의자료 기준 (🚧 아직 내 코드로 옮기지 않음)
package jpabook.jpashop.api;

/**
 * xToOne(ManyToOne, OneToOne) 관계 최적화
 * Order -> Member
 * Order -> Delivery
 */
@RestController
@RequiredArgsConstructor
public class OrderSimpleApiController {

    private final OrderRepository orderRepository;

    /**
     * V1. 엔티티 직접 노출
     * - Hibernate5Module 모듈 등록, LAZY=null 처리
     * - 양방향 관계 문제 발생 -> @JsonIgnore
     */
    @GetMapping("/api/v1/simple-orders")
    public List<Order> ordersV1() {
        List<Order> all = orderRepository.findAllByString(new OrderSearch());
        for (Order order : all) {
            order.getMember().getName();       // Lazy 강제 초기화
            order.getDelivery().getAddress();  // Lazy 강제 초기화
        }
        return all;
    }
}
```

`findAllByString(new OrderSearch())`는 [활용 1편 6장](../활용1/06.%20주문%20도메인%20개발.md)에서 만든 동적 쿼리 메서드다. `OrderSearch`를 빈 객체로 넘기면 조건이 하나도 안 붙어서 결국 `select o from Order o join o.member m` 전체 조회가 된다.

```java
// 내 코드 (OrderRepository)
public List<Order> findAllByString(OrderSearch orderSearch) {
    String jpql = "select o from Order o join o.member m";
    boolean isFirstCondition = true;
    ...
}
```

⚠️ 여기서 `join o.member m`은 **JPQL 조인일 뿐, `Member`를 함께 조회(select)하지 않는다.** `select` 대상은 `o` 하나다. 그래서 조인을 걸어도 `member`는 여전히 프록시로 남는다. 이 착각이 N+1을 못 보게 만드는 첫 번째 함정이다.

## 2. 엔티티를 직접 노출하면 안 되는 이유 (복습)

[1장](./1.%20API%20개발%20기본.md)에서 이미 다뤘다. 내 `Member` 코드에도 주석으로 남겨 놨다.

```java
// 내 코드 (Member)
// entity를 외부 api로 노출하면 안되는 2가지이유
// if) 필요에 의해 엔티티에 password를 추가하였다.
// 이때문에 1. 패스워드 노출, 2. api 스펙 변경 두가지 오류가 발생한다.
// private String password;
```

그런데 이 장의 V1은 그 위에 **지연 로딩이라는 새로운 문제**를 하나 더 얹는다. 아래 3~5절이 전부 그 이야기다.

## 3. 🔥 문제 1 — 프록시를 JSON으로 만들 수 없다

### 왜 터지는가

`Order`의 `xToOne` 연관관계는 활용 1편에서 전부 `LAZY`로 바꿔 놨다.

```java
// 내 코드 (Order)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "member_id")
private Member member;

@OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL)
@JoinColumn(name = "delivery_id")
private Delivery delivery;
```

지연 로딩이면 **DB에서 실제 `Member`를 조회하지 않는다.** 대신 하이버네이트가 만든 **프록시 객체**(`ByteBuddyInterceptor`가 들어간 가짜 `Member`)를 심어 둔다.

```mermaid
flowchart LR
    O["Order (진짜 엔티티)"] -->|member| P["Member$HibernateProxy<br/>ByteBuddyInterceptor"]
    P -.->|getName() 호출 시| DB[("DB 조회")]
    style P fill:#ffe0e0
```

Jackson은 이 프록시 객체를 만나면 **어떻게 JSON으로 만들지 모른다.** `Member`가 아니라 `Member$HibernateProxy$xxxx` 라는 처음 보는 타입이기 때문이다.

```
com.fasterxml.jackson.databind.exc.InvalidDefinitionException:
No serializer found for class org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor
```

### 해결 방법 두 가지

| 방법 | 설명 | 평가 |
|------|------|------|
| **A. 강제 초기화** | `order.getMember().getName()` 호출로 프록시를 실제 엔티티로 채운다 | V1 코드가 쓰는 방식 |
| **B. Hibernate 모듈 등록** | 초기화 안 된 프록시는 `null`로 출력하도록 Jackson에 알려준다 | 아래 4절 |

V1 컨트롤러의 이 두 줄이 바로 A다.

```java
order.getMember().getName();       // Lazy 강제 초기화
order.getDelivery().getAddress();  // Lazy 강제 초기화
```

💡 `getMember()`만 호출하면 **초기화되지 않는다.** 프록시는 껍데기를 반환할 뿐이고, `getName()`처럼 **실제 값이 필요한 메서드**를 호출해야 그 순간 DB 조회가 나간다. 프록시 동작 원리는 [기본편 8장 프록시와 연관관계 관리](../../jpaBasic/08.%20프록시와%20연관관계%20관리.md)에 정리해 뒀다.

## 4. 해결책 B — Hibernate 모듈 등록 (버전 주의)

강제 초기화를 일일이 쓰기 싫다면, Jackson에 하이버네이트 전용 모듈을 등록해서 **"초기화 안 된 프록시는 그냥 `null`로 뱉어라"** 고 시킬 수 있다.

### ⚠️ 여기가 강의와 가장 크게 갈리는 지점 — 버전 매트릭스

모듈 이름이 **부트 버전마다 다르다.** 강의는 부트 2.x 기준이라 그대로 따라 하면 안 된다.

| 환경 | 의존성 | `@Bean` 클래스 |
|------|--------|---------------|
| 부트 2.x (`javax`) | `jackson-datatype-hibernate5` | `Hibernate5Module` |
| 부트 3.x + Hibernate **5** (`jakarta`) | `jackson-datatype-hibernate5-jakarta` | `Hibernate5JakartaModule` |
| **부트 3.5 + Hibernate 6** ← 내 환경 | `jackson-datatype-hibernate6` | `Hibernate6Module` |

부트 3.0부터 `javax` → `jakarta`로 바뀌었기 때문에, 부트 3.x에서 구버전 `Hibernate5Module`을 쓰면 이렇게 터진다.

```
java.lang.ClassNotFoundException: javax.persistence.Transient
```

내 프로젝트는 **부트 3.5.16 → Hibernate 6.x** 이므로 `Hibernate5JakartaModule`도 아니고 **`Hibernate6Module`** 을 써야 한다.

```gradle
// build.gradle — 🚧 아직 추가 안 함
implementation 'com.fasterxml.jackson.datatype:jackson-datatype-hibernate6'
```

```java
// JpashopApplication — 🚧 아직 추가 안 함
@Bean
Hibernate6Module hibernate6Module() {
    return new Hibernate6Module();
}
```

이렇게 하면 **초기화된 프록시만 값이 나오고, 초기화 안 된 프록시는 `null`** 로 찍힌다.

> ⚠️ 이 절은 아직 실행해 보지 않았다. 실제로 의존성을 추가해 돌려 본 뒤 정확한 아티팩트명/클래스명과 로그를 확인해 갱신할 것.

### 강제 지연 로딩 옵션 — 있지만 쓰지 마라

```java
@Bean
Hibernate5Module hibernate5Module() {
    Hibernate5Module hibernate5Module = new Hibernate5Module();
    // 강제 지연 로딩 설정
    hibernate5Module.configure(Hibernate5Module.Feature.FORCE_LAZY_LOADING, true);
    return hibernate5Module;
}
```

`FORCE_LAZY_LOADING = true`는 **모든 지연 로딩을 전부 끌어온다.** 편해 보이지만 최악이다.

- `order → member`, `member → orders` 양방향 연관관계를 **계속 로딩**한다.
- 필요 없는 데이터까지 전부 조회하니 쿼리가 걷잡을 수 없이 늘어난다.

⚠️ 이 옵션을 켜면 무한루프를 막기 위해 **한쪽에 `@JsonIgnore`가 반드시 있어야 한다.**

## 5. 🔥 문제 2 — 양방향 연관관계의 JSON 무한 루프

엔티티를 직접 반환하면 Jackson이 객체 그래프를 **끝까지 따라간다.** 양방향이면 끝이 없다.

```
Order → member → orders(List<Order>) → member → orders → ... 💥 StackOverflow
Order → delivery → order → delivery → order → ... 💥
Order → orderItems → order → orderItems → ... 💥
```

### 내 코드 점검 — 현재 `@JsonIgnore`는 한 곳뿐

1장 작업 때 `Member`에만 걸어 놨다.

```java
// 내 코드 (Member)
@JsonIgnore // json 변환에서 제외해줌
@OneToMany(mappedBy = "member")
private List<Order> orders = new ArrayList<>();
```

`Order`를 직접 반환하려면 **나머지 두 곳도 막아야 한다.** 현재 상태로는 V1이 무한 루프에 빠진다.

| 엔티티 | 필드 | 현재 | V1에 필요한가 |
|--------|------|------|--------------|
| `Member` | `orders` | ✅ `@JsonIgnore` | — |
| `Delivery` | `order` | ❌ 없음 | ✅ **추가 필요** |
| `OrderItem` | `order` | ❌ 없음 | ✅ **추가 필요** |

```java
// 내 코드 (Delivery) — 🚧 @JsonIgnore 추가 필요
@OneToOne(mappedBy = "delivery", fetch = FetchType.LAZY)
private Order order;
```

```java
// 내 코드 (OrderItem) — 🚧 @JsonIgnore 추가 필요
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id")
private Order order;
```

⚠️ **엔티티를 직접 노출할 때는 양방향 연관관계가 걸린 곳은 꼭 한 곳을 `@JsonIgnore` 처리해야 한다. 안 그러면 양쪽을 서로 호출하면서 무한 루프가 걸린다.**

⚠️ 그런데 이건 **본질적으로 잘못된 처방**이다. `@JsonIgnore`는 순수한 도메인 엔티티에 **화면/API 표현 관심사를 침투시키는 어노테이션**이다. 엔티티가 Jackson에 오염된다. → 그래서 V2에서 DTO로 간다.

## 6. ⚠️ 절대 하면 안 되는 해결책 — EAGER로 바꾸기

"지연 로딩이 문제니까 즉시 로딩으로 바꾸면 되지 않나?" — **안 된다.**

| 이유 | 설명 |
|------|------|
| 필요 없는 조회 | 연관관계가 필요 없는 API에서도 데이터를 **항상** 조회한다 |
| 성능 튜닝 불가 | 어디서 어떤 쿼리가 나갈지 **예측이 안 된다** |
| JPQL의 함정 | `select o from Order o` 한 줄이 **N+1 쿼리로 폭발**한다 |

특히 마지막이 치명적이다. `EAGER`여도 **JPQL은 즉시 로딩을 고려하지 않고** 일단 `select * from orders`를 그대로 날린다. 그 후에야 결과 N건 각각에 대해 연관 엔티티를 채우려고 추가 쿼리를 N번 날린다.

> ✅ **원칙: 항상 지연 로딩을 기본으로 하고, 성능 최적화가 필요한 경우에는 페치 조인(fetch join)을 사용해라!** (V3에서 다룬다)

이건 활용 1편부터 지켜 온 원칙이고, [2장 정리 마지막](./2.%20API%20개발%20고급%20-%20준비.md)에도 적어 둔 내용이다.

## 7. V1의 쿼리 수 세어 보기

2장에서 만든 샘플은 **주문 2건**이다. `/api/v1/simple-orders` 호출 시:

```
1) select ... from orders o join member m            ← 주문 목록      1번
2) select ... from member where member_id = ?        ← order1의 회원  1번
3) select ... from delivery where delivery_id = ?    ← order1의 배송  1번
4) select ... from member where member_id = ?        ← order2의 회원  1번
5) select ... from delivery where delivery_id = ?    ← order2의 배송  1번
```

**총 1 + 2 + 2 = 5번.** 이것이 `1 + N + N` 이다.

⚠️ 주문이 100건이면 **201번**이 나간다. 이 숫자를 눈으로 확인하려고 2장에서 주문을 굳이 2건 만들어 둔 것이다.

💡 쿼리 로그는 `application.yml`의 아래 설정과 p6spy로 확인한다.

```yaml
# 내 설정 (application.yml)
logging.level:
  org.hibernate.SQL: debug
  # 쿼리 파라미터 로그 (스프링 부트 3.x, hibernate6)
  # org.hibernate.orm.jdbc.bind: trace
```

💡 영속성 컨텍스트가 1차 캐시로 잡아 주기 때문에 **같은 회원이 주문한 건은 추가 쿼리가 안 나간다.** 그래서 실제 쿼리 수는 "최악의 경우 N번"이다. 2장 샘플은 userA/userB가 각각 1건씩이라 캐시 효과가 없어서 정확히 5번이 나간다.

## 8. 결론 — V1은 쓰지 마라

강의 원문 그대로다.

> **결론: 엔티티를 API 응답으로 외부로 노출하는 것은 좋지 않다.**
> 그래서 `Hibernate5Module`(내 환경은 `Hibernate6Module`)를 사용하기 보다는 **DTO로 변환해서 반환하는 것이 더 좋은 방법**이다.

V1은 "이렇게 하면 된다"가 아니라 **"이렇게 하면 이런 문제가 터진다"** 를 보여주려고 존재하는 코드다. 실무에서 이 API를 그대로 쓰면:

- 프록시 직렬화 예외를 막으려고 → 라이브러리 추가 + `@Bean` 등록
- 무한 루프를 막으려고 → 엔티티마다 `@JsonIgnore` 도배
- 그러고도 → 필요 없는 필드 전부 노출 + N+1 쿼리

**전부 다 하고도 결과가 나쁘다.** 다음 절에서 DTO로 간다.

## 9. 🚧 V2 — 엔티티를 DTO로 변환 (미구현)

`SimpleOrderDto`를 만들어 필요한 필드만 담는다. 쿼리 수는 V1과 동일한 `1 + N + N`이라, **노출 문제만 해결되고 성능 문제는 그대로 남는다.**

⚠️ 내 `Order` 엔티티는 상태 필드명이 강의(`status`)와 달리 **`orderStatus`** 다. DTO를 만들 때 `order.getOrderStatus()`로 써야 한다.

```java
// 내 코드 (Order)
@Enumerated(value = EnumType.STRING)
private OrderStatus orderStatus; // order or cancel
```

`join fetch`로 `Order`·`Member`·`Delivery`를 **쿼리 1번**에 가져온다.

| 2 | 지연 로딩 필드는 **진짜 엔티티가 아니라 프록시**다 | Jackson이 직렬화 못 해 `InvalidDefinitionException` |
| 3 | 프록시는 `getName()`처럼 **값이 필요한 메서드**를 호출해야 초기화된다 | `getMember()`만으론 껍데기 |
| 4 | 모듈 이름은 **부트/하이버네이트 버전마다 다르다** | 부트 3.5 + Hibernate 6 → `Hibernate6Module` |
| 5 | `FORCE_LAZY_LOADING`은 쓰지 마라 | 필요 없는 연관관계까지 전부 로딩 |
| 6 | 양방향은 **한쪽에 `@JsonIgnore`** 가 없으면 무한 루프 | 현재 `Member`만 되어 있음 → `Delivery`·`OrderItem` 추가 필요 |
| 7 | 지연 로딩을 피하려고 **`EAGER`로 바꾸면 안 된다** | JPQL이 즉시 로딩을 무시하고 N+1을 그대로 만든다 |
| 8 | 정답은 **LAZY 기본 + 필요할 때 페치 조인** | V3 |
| 9 | V1 쿼리 수 = **1 + N + N** (주문 2건 → 5번) | 2장 샘플 데이터로 검증 |
| 10 | 결론: **엔티티를 API로 노출하지 마라** | 모듈·`@JsonIgnore`를 다 해도 성능 문제는 남음 |

> 다음: 엔티티를 DTO로 바꾼다. 다만 **쿼리 수는 하나도 안 줄어든다**는 것을 확인하는 게 V2의 포인트다.
